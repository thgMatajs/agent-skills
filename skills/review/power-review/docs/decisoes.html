Encadeamento e ramificações

Cada pergunta abaixo define um fluxo distinto. Use esta página para saber o que a skill faz (ou pula) em cada situação — modo, escopo, Figma, publicação e labels.

→

Ordem de avaliação no encadeamento: entrada → modo → side-effects start → escopo → Figma → research código → docs oficiais → prior → publish → finish → cleanup.

D1 · Qual a entrada?

pergunta

O usuário passou URL/IID de MR ou pediu review de branch local?

MR (URL / IID)

mode = mr

glab mr view <IID> --output json. Usar sempre source_branch, target_branch e diff_refs do GitLab.

>

Segue para D2 (estado do MR).

branch / “desta branch”

mode = local (default)

Se a branch já tem MR aberto e o usuário pediu publish → preferir mr. Se pediu só review local → permanece local, mas herda o target do MR.

>

Segue para D3 (resolver target local).

D2 · Estado do MR (só mode=mr)

pergunta

state == opened?

sim · opened

Side-effects start habilitados

Label stat:under review, reviewer atual, Jira → Code Reviewing. Depois: escopo + análise + publish possível.

não · merged / closed / locked

Avisar e pular workflow

Sem labels/Jira. Review de código ainda pode rodar se o usuário insistir; publicação fica sob critério explícito.

D3 · Resolver target (só mode=local)

ordem fixa

Qual target usar para origin/<target>...HEAD?

1º

MR aberto da branch

Usar target_branch do MR encontrado via glab.

2º

Defaults do repo

Entre develop / master / main existentes: ancestral real (merge-base / menor distância).

3º

Ambíguo

Perguntar — nunca assumir.

!

Local: sem post_review.py, sem side-effects. Entrega só no chat.

D4 · Escopo do diff (re-review)

script

resolve_review_scope.py encontrou marcador <!-- power-review:head_sha= -->?

sem marcador

mode = full

Diff: origin/<target>...origin/<source> (ou HEAD no local).

com marcador

Comparar last_head × current_head

sub-pergunta

SHAs diferentes?

sim

mode = incremental

Diff: <last_head>...<current_head>. Nota: “incremental desde <sha7>”.

iguais

mode = noop

Informar: nada novo. Só reanalisar full se o usuário pedir force-full.

*

Mesmo em incremental: ler arquivos completos tocados. Inline só em linhas adicionadas do diff em escopo.

D5 · Encadeamento Figma

após Context Pack

O pack trouxe URL de Figma (ticket ou pai)?

sim · tem link

Disparar subagente Figma × código

Task generalPurpose. Foco: fidelidade layout/tokens — não code review geral. Divergências → achados CRÍTICO…BAIXO.

não · sem link

PULAR passo 5

Anotar na nota/preview: “sem referência de Figma”. Seguir análise.

∥

Se o pack bloquear/degradar: registrar na nota e seguir o review (não travar o pipeline).

D-Research · Codebase / reuso

persona §8.2

Preciso mapear código reutilizável (funções, extensions, utils, padrões, testes) além dos arquivos do diff?

sim · research necessário

Buscar no repo antes de emitir achados DRY/reuso

Alvo típico: symbols similares, extensions Kotlin, helpers de camada, chamadores, leituras de cache, testes do fluxo crítico.

sub-pergunta

O escopo é grande o suficiente para valer um subagente?

sim · escopo amplo

Delegar Task / generalPurpose

Subagente ad-hoc (não há skill/arquivo dedicado tipo prior-comments.md). Pedir mapa: arquivos, padrões, candidatos a reuso, camadas, testes. Orquestrador consome o mapa na análise.

não · escopo contido

Fazer inline no orquestrador

Grep/leitura no worktree + validação de hipóteses. Default da skill (“Busque no repo para validar hipóteses…”).

mínimo sempre

Pelo menos ler arquivos do diff por completo

Research zero fora do diff é frágil para DRY: risco de sugerir código que já existe. Preview/nota devem mencionar o resultado do research (o que deveria ter sido reutilizado).

i

Não existe um subagente permanente “research-reuse”. É passo da persona, executado inline ou delegado quando útil.

D-Research · Docs oficiais (referências)

persona §8.3 + SKILL.md

Há dúvida técnica ou o achado cita boa prática Android/Kotlin?

sim · pesquisar

Research inline pelo orquestrador

Rodar date para referência temporal. Buscar docs atuais em developer.android.com / kotlinlang.org (e Detekt rules se for smell). Incluir link na seção Referência do comentário.

>

Sem subagente dedicado. WebSearch/fetch fica no orquestrador.

não · achado óbvio de bug/camada

Pode omitir link de doc

Proibições absolutas e bugs evidentes não exigem doc oficial — mas se mencionar “boa prática”, o link é obrigatório.

≠

Isso é diferente do Context Pack / Figma: docs oficiais = guidelines Android/Kotlin; Figma = fidelidade de UI do ticket (subagente condicional).

D6 · Prior comments

pergunta

Estamos em mode = mr?

sim

Rodar subagente prior-comments

Para cada candidato: NOVO | DUPLICADO | REFORÇO. Publicar só NOVO + REFORÇO válidos.

não · local

Pular anti-duplicação GitLab

Não há discussions/notes de MR para cruzar.

D7 · Preview aprovado?

human gate

Usuário aprovou o preview?

aprovado

Segue para D8 (publicar)

Preview deve incluir Comparing line, aderência, Figma, modo, achados, omitidos e status Detekt.

recusado / cancelado

Não publicar

Não aplicar requested_change. Ir direto ao cleanup da worktree.

D8 · Canal de entrega

pergunta

mode = mr?

sim

post_review.py

Discussions inline + nota-resumo. Summary deve terminar com o marcador power-review:head_sha.

>

Segue para D9 (finish / requested_change).

não · local

Entregar só no chat

Não chamar post_review.py. Não aplicar finish de labels. Cleanup da worktree.

D9 · Label requested_change (pós-publish)

após dedupe

Lista final tem ≥1 achado CRÍTICO, ALTO ou MÉDIO?

sim · blocking

finish --has-blocking-findings true

Adiciona label requested_change. Nunca no início do review.

não · só BAIXO / zero

finish --has-blocking-findings false

No-op de label. Não remove requested_change antiga automaticamente em re-reviews limpos.

D10 · Cleanup (sempre)

terminal · obrigatório

Independente de noop, cancelamento, falha parcial de side-effects ou modo local: 

git worktree remove --force "$WT"

Matriz rápida de fluxos

Fluxo Side-effects Prior / publish Entrega
MR opened · full start + finish condicional sim / sim GitLab inline + nota
MR opened · incremental start + finish condicional sim / sim só delta + marcador novo
MR opened · noop start (já rodou) · sem publish n/a avisar usuário
MR closed/merged não sob pedido caso a caso
Local não não / não somente chat

Research — inline vs subagente

Tipo de research Executor Obrigatório?
Codebase / reuso (functions, extensions…) Inline (default) ou subagente ad-hoc Sim na prática (DRY); delegação opcional
Docs oficiais Android/Kotlin Inline (orquestrador) Quando há dúvida ou citação de boa prática
Figma × implementação Subagente dedicado Só com URL no Context Pack
Prior comments Subagente dedicado Só mode MR/PR com can_resolve
Context Pack Jira/Figma fetch_context_pack.py Token primeiro; MCP só no fallback
