O que é a power-review

Skill pessoal de review crítico para Merge Requests do GitLab ou branches locais. Tolerância zero em bugs, ambiguidades, gambiarras e violações de SOLID / KISS / YAGNI / DRY — com Context Pack Jira/Figma, re-review incremental e side-effects de workflow.

pt-BR modo MR modo local Android / Kotlin Detekt
!

Trigger: pedido de power review, power-review, re-review, “review desta branch”, ou URL/IID de MR. A skill tem disable-model-invocation: true — só entra quando pedida.

Dois modos de entrega

mode = mr

Merge Request

Publica discussões inline + nota-resumo via glab / post_review.py. Aplica side-effects (labels, reviewer, Jira).

Entrada: URL ou IID (.../merge_requests/2457, 2457).

mode = local

Branch local

Entrega o review somente no chat. Não publica, não chama post_review.py, não mexe em labels/Jira.

Entrada: “review desta branch”, nome da branch, ou tip sem MR.

Pilares da análise

01

Persona + stack

Regras centrais iguais em qualquer stack (references/persona.md). Overlay e docs oficiais vêm de detect_stack.py + .power-review/stack.json.

02

Linter do repo

Smell/estilo só com o linter da stack detectada (Detekt, SwiftLint, ESLint, Ruff, …) e as regras anti-FP em references/linters.md.

03

Context Pack

Jira + Figma via skill jira-figma-context (opcional, profile review). Sem a skill, o review segue sem pack.

Checklist operacional

  1. Stack detect_stack.py --write → .power-review/stack.json + overlay da persona.
  2. Resolver entrada MR IID/URL ou branch local + source/target/SHAs.
  3. Side-effects start Se MR aberto: label stat:under review + reviewer + Jira Code Reviewing.
  4. Escopo do diff full | incremental | noop via marcador HTML.
  5. Context Pack Delegar a jira-figma-context se existir; senão pular.
  6. Figma × código Subagente só se houver URL Figma no pack; senão pular.
  7. Fetch + worktree Worktree da source tip em /tmp/pr-*.
  8. Leitura completa Arquivos alterados inteiros + carregar detekt.yml.
  9. Detekt (opcional) Rodar nos módulos tocados; usar saída como evidência.
  10. Prior comments Só MR: classificar NOVO / DUPLICADO / REFORÇO.
  11. Analisar Persona + Detekt + aderência ticket + Figma.
  12. Ancorar achados Severidade, path, new_line no head.
  13. Preview + aprovação Publicar só após OK do usuário.
  14. Publicar ou chat MR → post_review.py; local → só chat.
  15. Side-effects finish Se ≥1 CRÍTICO/ALTO/MÉDIO → label requested_change.
  16. Cleanup Remover worktree — sempre.
∥

Passos 4–5 podem rodar em paralelo com 6–7. O passo 5 depende do pack (presença de link Figma).

Research de codebase (reuso) e docs oficiais — inline vs subagente — na árvore de decisões.

Severidades

CRÍTICO ALTO MÉDIO BAIXO

Achados bloqueantes para a label requested_change são CRÍTICO, ALTO ou MÉDIO (após dedupe). Só BAIXO ou zero achados → não adiciona a label.
