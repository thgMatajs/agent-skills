Regras que a skill valida

Catálogo do que o reviewer aplica no diff/código. Fonte: references/persona.md, references/linters.md e heurísticas de reference.md.

proibição absoluta checklist anti-bug arquitetura Detekt / estilo
!

Bugs e violações de camada têm tolerância zero mesmo sem regra Detekt. Smell/estilo só sobe se a regra estiver active e estourar threshold do repo.

Proibições absolutas

gates
  • --no-verify ou burlar hooks/gates
  • Commit sem passar pelo gate
camadas
  • Regra de negócio em ViewModel ou Composable
  • Acesso a Room na camada de presentation
  • @Suppress / warnings ignorados para esconder falha estrutural

Padrões inegociáveis do projeto

01

Clean Architecture

Na variação já adotada pelo projeto — não reinventar camadas.

02

MVVM + MVI

Compatível com o padrão existente no código tocado.

03

Compose

Alta performance, baixo acoplamento, responsabilidades separadas.

  • Arquivos coesos Responsabilidade única, tamanho contido — nada de arquivos gigantes.
  • Testes de comportamento real Cobrir o fluxo crítico com efeito colateral observável.
  • Reuso obrigatório Nunca duplicar código nem criar abstração desnecessária.

Princípios clássicos

SOLID KISS YAGNI DRY
Tema O que o reviewer procura
SOLID / contratos Camadas quebradas, responsabilidades misturadas, acoplamento indevido
KISS Complexidade sem ganho; “elegante” que obscurece o fluxo
YAGNI Abstração / generalização sem necessidade comprovada agora
DRY Duplicação quando já existe função, extension, util ou padrão no repo

Anti-overengineering radar

Antes de sugerir abstração, as três perguntas precisam de “sim”:

Q1

Existe necessidade real agora?

Q2

Há ≥ 3 ocorrências que justificam a extração?

Q3

O custo cognitivo da abstração compensa?

→

Qualquer “não” → manter solução concreta; não sugerir a abstração.

Checklist anti-bug (10 obrigatórias)

Antes de considerar o review pronto, validar no diff/código:

  1. Null / vazio / zero não tratados?
  2. Falha de banco sem tratamento claro?
  3. Ação é idempotente se disparada duas vezes?
  4. Risco de corrida de estado (race)?
  5. Funciona com muitos itens (escala)?
  6. Sair da tela no meio quebra consistência?
  7. Gravação parcial sem proteção (atomicidade)?
  8. Comportamento offline/local correto?
  9. Validação 100% no use case?
  10. Testes cobrindo o fluxo crítico?

Heurísticas adicionais

corretude

Null-safety, off-by-one, erros, bordas; concorrência (flatMapLatest/debounce; cancelamento.

Kotlin / Android

Dispatchers injetados, Result, imutabilidade, escopos, Compose performático.

cache

Chave completa, teto, invalidação, thread-safety.

não faça

Otimização prematura sem evidência; gambiarra que viola contratos; complexidade/acoplamento desnecessários.

Detekt — smell / estilo / naming

Fonte de verdade: config/detekt/detekt.yml (+ baseline) do repo sob review. Não é gosto pessoal do reviewer.

Regra anti falso-positivo Efeito
Regra active: false Não abrir achado só por esse critério
Abaixo do threshold Não comentar como smell Detekt
Arquivo em excludes Não aplicar a regra
Já no baseline sem regressão Não reabrir como novo smell (bugs reais ainda podem)

Severidade típica de puro estilo: BAIXO / MÉDIO. Só ALTO/CRÍTICO se houver impacto de bug, segurança ou contrato de camada.
